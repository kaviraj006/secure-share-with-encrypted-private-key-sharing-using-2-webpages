CRYPTOGRAPHIC WORKFLOW ARCHITECTURE

1. Out-of-Band Fingerprint Verification: Contacts are verified by comparing full SHA-256 fingerprints before exchanging keys to protect against Man-in-the-Middle (MitM) attacks.

2. X25519 DH Agreement: Ephemeral sender key + recipient one-time signed prekey establish forward-secure raw shared secret.

3. HKDF-SHA-256 Derivation: Key derivation binds sender ID, recipient ID, transfer ID, and prekey ID into a 256-bit wrapping key.

4. AES-256-GCM Envelope: File key is wrapped with 12-byte nonce and authenticated additional data. Sealed envelope is signed with sender's Ed25519 key.

✓ Zero-knowledge backend: Server never sees raw AES file keys or private identity keys.

THREAT MODEL & ZERO-KNOWLEDGE BOUNDARIES

Cryptographic Boundary: Private keys (Ed25519 identity key, X25519 prekey private keys, ephemeral secrets) are generated and stored strictly inside the browser vault (IndexedDB encrypted with PBKDF2-100,000 + AES-256-GCM).

Server Role: The Flask backend on Port 5001 operates as an untrusted public-key directory, one-time prekey registry, and encrypted envelope mailbox.

Inter-Portal Handoff: SecureShare File Storage (Port 5000) stores encrypted ciphertexts. SecureShare Key Exchange (Port 5001) coordinates authenticated key delivery.
